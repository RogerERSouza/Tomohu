# Tomohu 0.20.0 — Account workspaces and explicit synchronization

Baseline: main at `7dbf47bd683ee9aeafbace3d1a014c71a7fa4181`. Implementation branch: `feature/v0.20.0-accounts-sync`.

## Delivered behavior

- Optional email/password registration and login using the existing backend. Tokens/passwords are not persisted by application code. Reload and expiry require authentication again.
- Owner-scoped notebook discovery. Select an existing notebook or create an empty one. Sending the open notebook as another account notebook requires explicit confirmation and preserves the source.
- Account snapshots use separate owner/notebook cache keys. The guest key `task.notebook.v1`, schema 1, preferences and existing local functionality are retained.
- Editing saves to the browser. `Sincronizar agora` explicitly sends a version-checked replacement. This release does not silently synchronize or merge notebooks.
- Offline/authentication/validation failures preserve pending edits. Server conflicts pause sending until the user exports their copy and explicitly loads the remote version, or creates a separate server copy. Edits made while a request is pending remain dirty after its acknowledgement.
- Corrupt caches pause saving and offer raw cache export plus explicit remote recovery. Normal notebook JSON exports remain available. Raw cache envelopes are diagnostic recovery files, not ordinary notebook imports.
- Another tab writing the same account cache pauses saving and attempts to archive the open snapshot under a recovery key. Prefer one tab per notebook; local storage is not a transactional cross-tab database.
- API limits are checked without silently truncating user content. The server validates ownership, hierarchy, nested IDs, reminder dates/intervals and counter values independently.

## Architecture and constraints

See [ADR 0003](../architecture/0003-account-workspaces-and-explicit-sync.md). `App` composes guest/account workspaces. `NotebookView` retains notebook routing/rendering. Account UI/form state, authentication, sync lifecycle, storage envelopes, API I/O and domain limits have separate modules. Shared JSON download behavior replaces duplicated download code. No new dependency package or database migration is required.

Caches are unencrypted and survive logout to preserve pending work. People sharing a browser profile can inspect that profile's data; signing in is not local-storage encryption. Clearing site data can delete pending work. Export backups first.

Public API hosting, refresh tokens, password recovery, email verification, OAuth, background synchronization and multiwriter local merging are not part of this release. The GitHub Pages frontend stays in local mode until a separately deployed HTTPS API is configured.

## Windows setup — two terminals

Save a JSON backup through Ajustes before applying changes. From a clean main at the baseline, create the feature branch and apply the incremental patch:

```powershell
git switch main
git pull --ff-only origin main
git status --short
git switch -c feature/v0.20.0-accounts-sync
git apply --check .\tomohu-v0.20.0-accounts-sync-7dbf47b.patch
git apply .\tomohu-v0.20.0-accounts-sync-7dbf47b.patch
```

If the baseline differs or local changes exist, inspect them before applying. Do not commit downloaded `.patch` files.

Terminal 1 starts your existing PostgreSQL-backed API:

```powershell
cd backend
docker compose up -d
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

Use the existing backend `.env` and PostgreSQL database. Alembic should already be at head; 0.20 adds no migration. The API must be running for account operations.

Terminal 2, at the repository root:

```powershell
if (!(Test-Path .env.local)) { Copy-Item .env.example .env.local }
npm.cmd ci
npm.cmd run dev
```

Copy the template only if `.env.local` does not already contain your configuration. It defines the public local API origin, not database credentials or a signing secret. Restart Vite after changing it. Use a frontend address on localhost or 127.0.0.1 port 5173, or configure backend CORS explicitly for a different origin.

Open Ajustes. Create an account (15–128 character password), confirm sending a separate local copy, edit a note, and use `Sincronizar agora`. Log out and confirm the guest copy is unchanged. Log in again and select the account notebook to retrieve saved work.

## Automated validation

From the root:

```powershell
npm.cmd run lint
npm.cmd run format:check
npm.cmd test
npm.cmd run build
npm.cmd run typecheck
npm.cmd run test:e2e
.\backend\.venv\Scripts\python.exe -m ruff check backend scripts
.\backend\.venv\Scripts\python.exe -m ruff format --check backend scripts
cd backend
.\.venv\Scripts\python.exe -m pytest
cd ..
```

The regular browser suite uses mocked account errors; its two live-API cases are intentionally skipped there. Run them separately with the existing API on port 8000 stopped:

```powershell
.\backend\.venv\Scripts\python.exe scripts\run_live_e2e.py
```

That runner creates a temporary SQLite database and starts/stops its own API, migrations and browser preview. It does not change your normal backend `.env` or PostgreSQL data. For a dedicated PostgreSQL test database:

```powershell
$env:TOMOHU_E2E_DATABASE_URL = 'postgresql+psycopg://tomohu:tomohu@localhost:5432/tomohu_test'
.\backend\.venv\Scripts\python.exe scripts\run_live_e2e.py
Remove-Item Env:TOMOHU_E2E_DATABASE_URL
```

Create `tomohu_test` once if it does not exist. The runner rejects configured PostgreSQL databases whose names do not end in `_test`. The CI backend job runs both API tests and real browser integration on PostgreSQL 17.

## Manual checks and recovery

1. Confirm ordinary local creation/editing, backups, reminders, counters and preferences still work without any account.
2. Confirm login does not upload anything until an explicit copy action. Verify a second account cannot discover the first account's notebooks.
3. Edit an account notebook, stop the API, attempt synchronization and confirm the note remains. Restart the API and retry; if its temporary signing secret changed, log in again and reopen the pending account notebook.
4. Change the same server notebook from another client. Confirm a stale save reports conflict and does not overwrite it. Export the local version before using the confirmed remote reload or new-copy action.
5. Reload/login and confirm pending account edits remain separate from guest data. If storage is unavailable, export the open notebook before switching workspaces; the UI blocks switching until a backup of the current snapshot has been downloaded.
6. Check account controls on narrow mobile screens and both themes. Tokens/passwords must not appear in local/session storage or URLs.

Rollback: revert the release on its feature branch/main as appropriate. Guest storage remains readable by 0.19. Preserve/export account caches before rollback; older frontends do not understand their envelopes. Backend discovery is additive, but API clients relying on previously invalid snapshots must correct those records rather than bypass validation.

## Windows live-test cleanup correction

The Windows PostgreSQL run passed both browser scenarios, then failed deleting `api.log` with WinError 32. The runner now inherits console output instead of opening a temporary log, explicitly uses one API worker and stops its owned Windows process tree before temporary database cleanup. Cleanup failures remain visible. Lifecycle regression tests cover Windows tree shutdown, failure reporting, an already-exited process, forced shutdown and a real process exit.

Repeat `scripts/run_live_e2e.py` on Windows after applying this correction. Both browser scenarios and a clean runner exit are required; Linux checks do not replace native Windows verification.
