# 0.23.0 — Account-first access

Baseline: `97485b8aee85cf63600293d4386796b431199065`.

## Behavior

- Login, registration and recovery are the entry screen. Normal notebook editing requires an authenticated account. There is no anonymous-editor bypass when the API is unconfigured or unavailable.
- A new account receives an empty first notebook through an idempotent server bootstrap. Existing notebooks and ownership remain unchanged.
- A browser renewal cookie keeps the account available after reload. Access tokens remain memory-only and short-lived. The browser session has a fourteen-day absolute lifetime; logout, password reset/change and session revocation invalidate it.
- Existing guest data remains untouched. Export the original before login or explicitly copy validated data into a new account notebook after login. Nothing is uploaded or deleted automatically.
- A loaded common notebook remains available for read-only consultation during a connection failure. Editing, import, synchronization and private access are unavailable until online session validation succeeds. Reloading offline is not a supported PWA/cold-start workflow.
- Explicit logout or a confirmed authentication rejection returns to sign-in; neither is treated as permission to use offline mode. Pending account caches and private drafts remain isolated and preserved.
- Public synchronization remains manual; private autosave remains separate. Settings navigation and custom card ordering are not part of this release.

See [the feature specification](../specs/mandatory-accounts.md) and [ADR 0006](../architecture/0006-browser-account-access.md) for contracts, limits and recovery decisions.

## Environment and deployment

The API and PostgreSQL must be running for account access. Configure the root `.env.local` with the public API origin and keep real backend secrets in the untracked `backend/.env`. Never put secrets in Vite variables. Loopback API hosts are normalized to the frontend's loopback host for browser sessions in local development, avoiding mixed localhost/127.0.0.1 cookies.

Production renewable sessions require the API to be served through the same HTTPS origin as the frontend, usually using a reverse proxy for `/api`. A GitHub Pages frontend and unrelated API domain do not satisfy this requirement. Browser-session routes reject unsupported production origins; do not weaken cookie security or persist tokens in localStorage to work around that. Configure trusted proxies explicitly when terminating TLS upstream. Hosting is a separate operational task; local tests are not proof of production readiness.

## Apply and validate on Windows

Run from the repository root. Keep the working tree clean before applying the release patch. Stop manually started API/frontend processes before the live test runners, which own ports 8000 and 4173.

Frontend checks:

```powershell
npm.cmd ci
npm.cmd run lint
npm.cmd run format:check
npm.cmd test
npm.cmd run build
npm.cmd run typecheck
npx.cmd playwright install chromium
npm.cmd run test:e2e
```

Backend checks (Docker Desktop must be running):

```powershell
docker compose -f .\backend\docker-compose.yml up -d
if ($LASTEXITCODE -ne 0) { throw 'Database startup failed.' }
Push-Location backend
try {
    .\.venv\Scripts\python.exe -m pip install -e ".[dev]"
    .\.venv\Scripts\python.exe -m ruff check .
    .\.venv\Scripts\python.exe -m ruff format --check .
    $env:TOMOHU_TEST_DATABASE_URL = 'postgresql+psycopg://tomohu:tomohu@localhost:5432/tomohu_test'
    .\.venv\Scripts\python.exe -m pytest
    if ($LASTEXITCODE -ne 0) { throw 'Backend tests failed.' }
} finally {
    Remove-Item Env:TOMOHU_TEST_DATABASE_URL -ErrorAction SilentlyContinue
    Pop-Location
}
```

Real account and privacy browser tests:

```powershell
$env:TOMOHU_E2E_DATABASE_URL = 'postgresql+psycopg://tomohu:tomohu@localhost:5432/tomohu_test'
try {
    .\backend\.venv\Scripts\python.exe scripts\run_live_e2e.py

}
```

## Development database upgrade

Automated tests use isolated schemas; they do not upgrade the normal development database. Make and verify a database backup before applying migration `20261117_06` to existing data. Then run `python -m alembic upgrade head` with the backend environment. No notebook snapshot migration or guest-storage deletion is needed. Restart the API after upgrading.

Rollback must stop the new API/frontend first. The migration downgrade revokes browser sessions before dropping renewal records; notebooks remain intact. Do not clear browser storage as a rollback procedure.

## Manual acceptance

1. Open without a session: verify login/register/recovery, with no editable guest notebook.
2. Register and verify that exactly one empty notebook is available. Reload and verify session continuity.
3. With old guest data, export before login and explicitly copy after login; confirm the original is unchanged.
4. Edit a common notebook, disconnect and verify that navigation/reading remain possible but every mutation is disabled. Reconnect through Settings and verify that editing resumes only after validation.
5. Open a private item, edit and test privacy/account expiry recovery. Preserve/export drafts before destructive replacement.
6. Sign out and reload: normal notebook access must remain closed. Sign in again and confirm pending data survives.
7. Exercise email verification, password reset/change and session revocation; verify the corresponding sessions can no longer renew.

Never use a real personal account, production credentials or production database as test fixtures.
